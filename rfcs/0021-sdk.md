# RFC 0021: The SDK

- **Status:** Draft
- **Author:** Mateusz Pianka
- **Created:** 2026-10-06
- **Last changed:** 2026-10-06
- **Supersedes / superseded by:** —

## Summary

The kit for writing apps: C, Rust and AssemblyScript, in that order, with
bindings generated from the system's interfaces; one command-line tool,
`pdev`, that creates, builds, packages, signs, installs and debugs apps,
and serves AI coding assistants through MCP; a simulator and a light
runner for working without a device. WebAssembly apps come first; native
apps get their kit later.

## Problem

The RFCs so far leave these to the SDK:

- [RFC 0008](0008-runtime.md): apps are WebAssembly modules that export
  `init`, an event handler and their actions, call services with Protocol
  Buffers messages ([RFC 0005](0005-communication.md)), and use a small
  part of WASI; the manifest is written in TOML and compiled by the SDK's
  packaging tool.
- [RFC 0009](0009-packages.md): packages are signed with a developer key
  that the SDK makes.
- [RFC 0012](0012-developer-access.md): apps are installed with
  `adb install`; WAMR's debugger is designed with the SDK.
- [RFC 0017](0017-i18n.md): translations are `.po` files, compiled to
  `.mo`.
- [RFC 0019](0019-system-ui.md): screens are built from blocks, and a
  canvas.

The previous system measured, on the device: C fastest, AssemblyScript
about 4 times slower, and JavaScript or Python running inside
WebAssembly 50 to 500 times slower.

## Proposal

### Languages

| Language | Compiler |
|---|---|
| **C** | wasi-sdk (clang) |
| **Rust** | its `wasm32-wasip1` target |
| **AssemblyScript** | its own compiler, `asc`; TypeScript-like, for developers coming from the web |

These are the **supported languages**: the SDK has templates, bindings
and examples for each, and they are tested with every host API level.
Any other language that compiles to WebAssembly can use the documented,
language-neutral interface, untested, until it joins the list.

### Bindings

Bindings are **generated, not written:** from the services' `.proto` files
(RFC 0005) and the description of the runtime's own functions
(RFC 0008), one set for each supported language and each host API level.
An interface changes, and the bindings follow with the next SDK; nothing
lags behind by hand.

### `pdev`

One command-line tool on the developer's computer:

| Command | Does |
|---|---|
| `pdev new` | a project from a template, in a supported language |
| `pdev build` | builds the module with the language's compiler, and compiles the manifest and the translations |
| `pdev package` | makes and signs the package, `.wpk` (RFC 0009), with the developer's key, made on first use |
| `pdev install`, `pdev run` | installs the package on a device or the simulator, and starts it (through adb, RFC 0012) |
| `pdev log` | the app's logs |
| `pdev sim` | starts the simulator |
| `pdev debug` | attaches the debugger (below) |
| `pdev mcp` | serves the above to AI coding assistants (below) |

### For AI coding assistants

`pdev mcp` is an **MCP server** (the Model Context Protocol, which AI
coding assistants speak). It offers an assistant the same things a
developer has:

- creating, building, packaging and installing apps;
- running them in the simulator, reading their logs, and seeing the
  simulator's screen;
- the reference documentation and the bindings, for the host API level
  in use.

It can do nothing a developer could not: it acts only on the projects it
is pointed at, the simulator, and devices the developer has connected and
authorized (RFC 0012). On a device, every install still needs the owner's
confirmation on its screen (RFC 0009), so an assistant cannot install
anything unseen.

### Without a device

| | Is | For |
|---|---|---|
| **The simulator** | pnut-os itself, built for the computer with NuttX's simulator; the screen in a window, with e-paper's slowness imitated when asked | trying an app as it will run |
| **The light runner** | the runtime alone, with stand-in services | fast automated tests |

### Debugging

WAMR's debugger, through lldb: first on the simulator, then on a device
with Developer options on (RFC 0012). Logs come through `adb logcat`.

### Getting the SDK

- a **container image** with everything in it, for any system;
- **native packages** for Linux and macOS;
- **Windows** through WSL.

### Native apps

WebAssembly apps come first. A kit for native apps
([RFC 0002](0002-build-mode.md)) follows: made for each firmware build
from NuttX's export (the headers and libraries to build against), since
native apps are tied to the firmware they were built for (RFC 0009).

## Alternatives

- **JavaScript or Python as the first language.** The most familiar, but
  they run inside WebAssembly 50 to 500 times slower than C.
- **Every language at once.** More developers reached, but nothing
  tested properly.
- **Bindings written by hand.** Nicer in places, but always behind the
  interfaces.
- **One tool per task** (a builder, a packager, an installer). Each
  simpler, but more to learn and keep in step.
- **Only the simulator,** or **only the light runner.** The simulator is
  slow for automated tests; the light runner does not show how an app
  really runs.

## Costs and risks

- **Three languages to keep tested** with every host API level.
- **The simulator** must follow the firmware, or apps will behave
  differently on it.
- **An AI assistant through MCP** can build, run and read logs on its
  own; it is held to what the developer could do anyway, and installing on
  a device still waits for the owner's confirmation.
- **The native kit** comes later, so native apps wait.

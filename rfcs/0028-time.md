# RFC 0028: Time

- **Status:** Draft
- **Author:** Mateusz Pianka
- **Created:** 2026-10-23
- **Last changed:** 2026-10-23
- **Supersedes / superseded by:** —

## Summary

Time keeps the wall clock right and the time zone known. It takes the time
from the modem's network, from NTP or from GNSS, in that order of
preference. Between those readings it corrects for the error of the clock
that times light sleep, which it learns from them. The zone is a named one
the owner picks, or by default the network's offset. Wake timers and
alarms, also Time's ([RFC 0007](0007-services.md)), come in a later RFC.

## Problem

- **The clock gains while the chip sleeps.** Light sleep is timed by an
  internal RC oscillator that runs faster asleep than when it was
  calibrated: on the T-Deck Max the clock gains about 0.85 % of the time
  slept, up to about 12 minutes a day. The board has no 32 kHz crystal to
  time sleep instead.
- **Nothing sets the clock.** After a power loss it starts from a fixed
  date in the kernel's configuration (6 December 2011 today). The previous
  system ([current architecture](../current/architecture-v2.md)) set it
  from the modem's network time, or by NTP, every 6 hours, which still
  left minutes of error between settings, and none of it corrected
  offline.
- **There is no time zone.** Programs show UTC.

RFC 0007 makes Time the one keeper of the wall clock, the time zone,
network time and the timers that wake the device, as
[RFC 0004](0004-layers.md) asks. This RFC covers the clock and the zone.

## Proposal

### Where the time comes from

Time takes the best reading available. When several are at hand within
their uncertainty, it prefers them in this order:

| Source | From | When |
|---|---|---|
| **The modem's network** | Telephony, which reads the modem's clock, set by the network (`AT+CTZU=1`), with the network's offset and summer time | when the modem is registered and the network has sent the time; not every network does. Costs no data |
| **NTP** | Time itself, over the network | when Wi-Fi or mobile data is up already: Time never brings a connection up for the time |
| **GNSS** | Location | when the receiver has a fix, while something else uses it |
| **The owner** | the system UI's clock setting | when none of these has spoken |

- **Sources report their readings to Time,** each with its uncertainty
  (open question 1 says how).
- **Time reads NTP itself** when Network announces a connection that is
  up ([RFC 0015](0015-network.md)), from the server in its setting
  `ntp_server` (`pool.ntp.org` by default).
- **A reading is taken at most hourly,** at the device's next wake after
  the hour while a source is cheap to reach (the modem registered, a
  connection up); nothing wakes the device for the time. Reading the
  modem's clock keeps the chip awake about a second.

### Between readings: the sleep clock's rate

The crystal times the chip while it is awake, so only the time it sleeps
goes wrong, and by a fairly steady factor.

- **Time learns the factor.** At each reading it compares the clock's
  error with the time slept since the last reading, which NuttX's power
  management counts (`/proc/pm`), and keeps a smoothed estimate of the
  sleep clock's rate.
- **The kernel applies it** where it turns a light sleep's length into
  clock time (the Espressif layer of the NuttX fork), so the clock, the
  monotonic clock and the timers all come out right. How Time hands the
  factor to the kernel, and through which service, is open (question 6).
- **The factor is kept** in `/var/lib/time`, with the last good time
  (question 5), so a restart starts corrected, and a restart after a
  power loss starts near the right time, marked as not yet confirmed,
  rather than in 2011.

### The time zone

- **Time's settings** (owner `time`, [RFC 0025](0025-settings.md)):
  `zone`, an IANA zone name (`Europe/Warsaw`) that the system UI picks
  from the list of zones; `zone.auto`, on by default; and `ntp_server`.
- **With `zone.auto` on, the zone follows the network:** the offset and
  summer time the modem reports. A network-given offset has no rules for
  the future, but the network announces each change.
- **With it off, the named zone applies,** with its rules. The build
  compiles every zone of the tz database it is built with into its POSIX
  rule (`CET-1CEST,M3.5.0,M10.5.0/3`): 9 to 13 KB, depending on whether
  old names (links) are kept, in `/usr/share/zones`:
  [RFC 0010](0010-file-layout.md)'s `/usr/share` gains the zone rules.
  Old rules are not kept: dates long past may show an offset that was
  different then.
- **Programs learn of the zone from the `time` topic** (how they turn
  times into local ones is open question 3).

### What others see

- **The `time` topic** ([RFC 0005](0005-communication.md)) announces a
  change of the zone, and a step of the clock with its size, so that
  programs showing the time, or holding timers by the wall clock, redraw
  or re-arm.
- **The `pnut.Time` interface:** `Get` gives the time, the zone and its
  rule, the source of the last reading and when it was taken; `Set` sets
  the owner's own time. Callers are known by program
  ([RFC 0006](0006-manager.md)): only the `ui` program may `Set`.

Time is a module of the system program (RFC 0007).

## Rules it follows

- **One owner** of the clock (RFC 0004): nothing else sets it; others only
  report.
- **Readings come with events** (the modem registering, a connection
  coming up), and at most hourly while such a source is up, taken when the
  device wakes anyway: nothing wakes the device for the time. This bends
  RFC 0004's rule against polling as RFC 0007 does for the battery: a
  reading an hour costs about a second awake.
- **No connection for the time alone,** so the time costs neither data nor
  a radio's power.

## Alternatives

- **Re-setting the clock every few hours, without the rate.** Simpler, but
  minutes of error build up between settings, and without a source the
  clock just runs fast.
- **NTP only.** One mechanism, but offline (most of the time) the clock
  drifts, and the modem's free network time goes unused.
- **A 32 kHz crystal.** The cure, but the board has none; the next device
  should.
- **Correcting with `adjtime()`.** The ESP32-S3 port does not support it,
  and it would correct only the wall clock, not the timers that sleep
  delays too.
- **Only an offset setting.** Smallest, but the owner would change it
  twice a year.
- **`zone.auto` from the network's country** (its MCC) and offset, as the
  previous design had: it gives the zone's rules, so summer time comes
  right offline. Following the offset was chosen instead; this stays an
  option for later.
- **The whole tz database, with its history.** Exact for old dates, but
  hundreds of kilobytes.

## Costs and risks

- **9 to 13 KB** of zone rules in the image; a module in the system
  program.
- **A patch in the fork's Espressif layer** to apply the factor. The
  sleep's length comes from the slow clock's calibration in Espressif's
  HAL, which the Wi-Fi and Bluetooth drivers also read: scaling it there
  would move the radios' sleep timing too, so the factor is applied after
  it, to the clock alone.
- **The learned factor is only as good as the readings:** the RC
  oscillator's error changes with temperature. Smoothing, and readings
  every hour when they are free, keep it close; how close is to be
  measured.
- **A network may give a wrong time.** With two sources, a reading far
  from the other's is set aside; with one, a reading far from the clock
  as corrected (more than a few minutes, to be measured) is held until a
  second agrees. The first reading after a power loss is taken as it is.
- **Telephony and Location do not exist yet:** until they do, the time
  comes from NTP and the owner, and the rate keeps it between them.

## Open questions

1. **How sources report: calls or topics.** Telephony and Location could
   call a `Report` method (Time checks the caller's program), or publish
   `network_time` and `gnss_time` topics that Time reads. RFC 0004's rule
   that information comes up as events favours topics, which also need
   no caller check. Recommended: topics.
2. **NTP's name lookup.** RFC 0015 gives Network the name lookups: Time
   asks Network for `pool.ntp.org`'s address, or resolves it itself with
   the kernel's resolver. Recommended: ask Network, as RFC 0015 says.
3. **Local time in programs and apps.** NuttX's `localtime()` takes one
   zone for the whole system (`LIBC_LOCALTIME`, a few KB of tables), while
   a calendar needs many zones at once. Recommended: the service library
   converts with the rules itself, any zone by name, and the runtime gives
   apps the same ([RFC 0008](0008-runtime.md)); `LIBC_LOCALTIME` stays
   off.
4. **`zone.auto` without a network.** A summer-time change while the
   modem is unregistered, or on a device without a modem (RFC 0004 lets
   it lack one), passes unnoticed.
   Recommended: until the network gives an offset, auto uses the named
   zone, whose rules then apply.
5. **Manual time against network time.** Recommended: the owner's time is
   a fallback, replaced by the next reading from a source; an "automatic
   time" switch is not needed.
6. **The factor's path to the kernel,** and what is written when. Power
   owns the decision to sleep (RFC 0007): Time gives Power the factor, and
   Power gives it to the kernel. Time's state is written with each reading
   (at most hourly, a few bytes) and as the program stops. The chip's own
   RTC keeps counting across a restart without power loss, so the clock
   needs no file then.
7. **How large a step** the clock takes at once, rather than catching up
   through the rate.

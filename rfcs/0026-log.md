# RFC 0026: Log

- **Status:** Accepted
- **Author:** Mateusz Pianka
- **Created:** 2026-10-08
- **Last changed:** 2026-10-29
- **Supersedes / superseded by:** —

## Summary

One log for everything, through NuttX's syslog: each line with its time,
level and program, apps marked by the runtime. The lines go into a RAM
ring that survives a reset; the Log service copies warnings and above into
rotated files, saves a crash report after a crash, and serves the log
filtered by level and by service or app, each of which has a level that
changes live. Nothing private is logged above debug.

## Problem

- [RFC 0007](0007-services.md) gives Log the logs kept across restarts,
  and notes that NuttX's own log is a ring in RAM.
- [RFC 0010](0010-file-layout.md) puts the files in `/var/lib/log`, with
  `/var/log` a link to it.
- [RFC 0012](0012-developer-access.md) reads logs live with
  `adb logcat`, and pulls crash reports with adb;
  [RFC 0013](0013-firmware-updates.md) counts on crash reports.
- [RFC 0008](0008-runtime.md) has the runtime mark apps' lines with the
  app's identity.

NuttX offers syslog with eight priorities, and options that add the time,
the priority and the program's name to each line; a RAM log whose buffer
can be placed in a chosen section of memory; a file channel with
rotation; a stack dump and a backtrace when an assertion fails, a reset
afterwards, and core dumps to flash.

## Proposal

### One stream

Everything logs through **NuttX's syslog:** the kernel, drivers, services,
and apps through the runtime.

- **Each line carries** the time, the level, and the program's name
  (NuttX's `SYSLOG_TIMESTAMP`, `SYSLOG_PRIORITY` and
  `SYSLOG_PROCESS_NAME`, in the configuration fragment,
  [RFC 0022](0022-build.md)); the service library's log call
  ([RFC 0023](0023-service-library.md)) adds the module's name, and the
  runtime adds the app's id (RFC 0008).
- **One stream, one place to read:** a problem that crosses programs is
  read in order.

### The RAM log

Lines go into **NuttX's RAM log,** a ring sized for each device, placed
in a section of external RAM that **survives a reset** where the chip
keeps external RAM across one (NuttX's `RAMLOG_BUFFER_SECTION`), so the
last lines before a crash are there at the next start. A chip that does
not keep it uses a smaller ring in internal RAM.

Where external RAM sits behind a data cache, the RAM log writes each line
back to the RAM as it is logged, so that a reset the system did not ask
for, a watchdog's or one a flashing tool gives through the serial port,
loses no finished line; before a reset the system asks for, the whole
cache is written back.

### Levels

| Level | For |
|---|---|
| **error** | something failed, and someone should look |
| **warning** | something unexpected, handled |
| **info** | what the system did: started, connected, installed |
| **debug** | what a developer needs to follow the code |

Syslog's eight priorities map onto these four: emergency, alert and
critical count as errors, notice as info. **Each service and app has a
level,** a setting of its own ([RFC 0025](0025-settings.md)) that changes
live: the library filters lines below it before they reach syslog. The
default is info; debug is off.

- **The setting is `log.level`,** in the settings of each service and app
  (its *owner,* in RFC 0025's term): a choice of error, warning, info and
  debug, not marked public.
- **Every service and app has it** without declaring it: the service
  library adds it to a service's schema (RFC 0023), the runtime to an
  app's (RFC 0008). A service that declares no settings still registers a
  schema of its own, holding this one.
- **A change takes effect at once,** through the settings topic, without
  a restart.
- **The kernel and the drivers** log at the levels chosen when the
  firmware is built (NuttX's options), which no setting changes.

### Kept across restarts

The **Log service,** in the system program (RFC 0007), follows the RAM
log and copies lines into **`/var/lib/log`:**

- **warnings and above by default,** to spare the flash; a Developer
  option keeps every line, and another writes a copy to a `logs` folder
  on the external storage the device's owner picks;
- **rotated files** (`system.log`, `system.log.1`, …) under a total cap
  (below);
- **writes gathered** on the program's worker, every few seconds or when
  its buffer fills, and at an orderly shutdown; between writes the RAM
  log holds the latest lines.

### Rotation

- **By size, not by time.** `system.log` is appended to until it reaches
  its cap. Then the oldest file is deleted and the others move up one
  (`system.log.2` to `.3`, `.1` to `.2`, `system.log` to `.1`), and a new
  `system.log` starts. The number of files and their size bound the flash
  exactly, whatever the device does; time would not.
- **Rotation copies nothing:** on littlefs a rename is a change of
  metadata, made atomically, so a reset in the middle leaves whole files.
- **A restart starts no new file.** Log appends, so the sequence across
  restarts is read in one place, and writes **marks** of its own, which
  start `----` as no line of the RAM log does:
  - `---- start <time>, <firmware> ----` where each start's lines begin;
  - `---- stop <time> ----` when the program stops in order, so a start
    with no stop before it follows a reset, a crash or a loss of power;
  - `---- <n> lines not kept: no room ----` when lines came faster than
    Log could write them.

  Times in the marks are UTC; the lines' own times count from the
  device's start.
- **Lines a reset cut off** are not lost: as it starts, Log copies the
  lines the RAM log kept after the last one the files have (among them
  the lines of the start before, up to the reset), and puts this start's
  mark before this start's first line.
- **Crash reports are apart** from the rotation: `crash-<time>` files are
  kept up to their own number, the oldest deleted first.
- **The copy on external storage** rotates the same way, with larger
  files, since space there is plentiful.
- **Log's interface reads the rotated files as one sequence,** oldest
  first; a position is a file and an offset, so a reader goes on where it
  stopped, across a rotation.

### Crashes

1. **When an assertion fails,** NuttX dumps the stack and a backtrace into
   the RAM log (`ARCH_STACKDUMP`, `SCHED_BACKTRACE`), and resets the
   device when the crash is the kernel's (`BOARD_RESET_ON_ASSERT`, below).
2. **Log recognises a crash by its dump:** NuttX writes the assertion and
   the stack and task dumps at the alert level or above, which it uses
   for little else: the processors' fault handlers and the sanitizers,
   whose lines are a crash's too. A dump in the RAM log with no line
   after it saying it is saved (`log: Crash report saved`) is saved as a
   report: the RAM log's last lines up to the dump's end, at most a set
   size. A report kept already that ends with the same line counts as
   saved, since a reset can lose the line saying so. Of a dump,
   `system.log` keeps only the assertion's line; the rest is the
   report's.
   - **At the next start,** when the crash reset the device: NuttX resets
     it for a crash in an interrupt or in one of its own threads, a
     processor fault among them, which NuttX's fault handlers count as
     one.
   - **While Log runs,** once the dump has been quiet a second, when the
     crash ended one task of a program and not the device: an assertion
     failed in it.

   A report is **`/var/lib/log/crash-<time>`,** named by the time Log
   finds it, in UTC, since the dump's lines carry only the time since the
   device's start; a name taken already gets a number. Log keeps the last
   few such files.
3. **The device's owner is told** through Notifications
   ([RFC 0020](0020-notifications.md)), and can read or share the report
   from the Logs screen; developers pull it with adb (RFC 0012).

A **full core dump** is a Developer option: it is large, so it is written
to external storage when one is present.

### Reading

- **`adb logcat`** reads the RAM log live (RFC 0012); `pdev log` uses it
  ([RFC 0021](0021-sdk.md)).
- **Log's interface** reads from a position on, filtered by level and by
  service or app, a page at a time ([RFC 0005](0005-communication.md)): for
  the system UI's **Logs screen,** under Developer options, and for tools.

### Discipline

- **Privacy:** message text, phone numbers, keys and passphrases are never
  logged above debug, in what a service writes itself. A field marked
  **sensitive** in a `.proto` file is redacted by the generated code
  (RFC 0023) whenever a message is logged, at every level, debug
  included, so the rule holds without each service remembering it. A
  setting marked secret (RFC 0025) is sensitive too: it shows only as its
  tag, never as itself.
  - **The field is replaced by a short tag:** the same for the same value
    within one boot of the device, made with one key for all programs,
    drawn at random at each boot. The lines show that two values are the
    same without showing either, and the value cannot be found by trying
    each possible one, as a phone number could be from a plain hash.
- **Bounds:** a line is cut at a set length; a service or app logging
  faster than a set rate has its lines dropped and counted, and one line
  says how many, so none of them floods the ring.

### Starting values

Set for each device; to be measured:

| What | Value |
|---|---|
| The RAM log | 64 KB |
| Files in `/var/lib/log` | 4 files of 64 KB: 256 KB in all |
| The copy on external storage | 8 files of 1 MB |
| A line | 160 characters |
| Lines per service or app | 50 a second |
| Writes to flash | every 5 s, or when 8 KB is waiting |
| Crash reports kept | 5 |
| A crash report | 16 KB |

## Alternatives

- **NuttX's file channel** writing every line to flash as it is logged.
  Simpler, but slow, and the flash would wear with every debug line.
- **A Log service that receives lines over sockets** instead of syslog.
  Richer lines, but every line a message, and the kernel's and drivers'
  lines elsewhere.
- **A log per service.** Easier to find one service's lines, but a problem
  that crosses programs could not be read in order.
- **Keeping everything in flash.** Nothing lost, but flash wear, and the
  files full of debug.
- **A console only.** Nothing kept, and nothing without a cable.

## Costs and risks

- **64 KB of RAM** for the ring, on every device.
- **Power loss loses the ring;** only a reset keeps it. The files hold
  what was copied before.
- **Flash wear** in proportion to warnings and errors; a service that
  warns in a loop wears it, until its rate limit drops the lines.
- **Redaction depends on marking fields;** an unmarked field logs as it
  is.
- **A crash before Log starts** is kept in the ring, and saved at the
  start after that.
